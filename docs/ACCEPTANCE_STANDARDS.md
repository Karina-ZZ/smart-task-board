## 1. 一句话原则

> **一个功能只有同时满足本文档列出的全部条件，才会被报告为「开发成功」并提交验收；提交前必须完成全量功能回归。**

## 2. 单功能「开发成功」的硬性条件（共 10 条，每条都必须达成）

| # | 条件 | 本项目的可执行判据 |
|---:|---|---|
| 1 | **页面与组件与第二版 HTML 一致** | 视觉、布局、组件结构、控件种类、文案与 `docs/reference/02-第二版-智能任务看板前端.html` 逐一对照；不允许私加私删入口。差异需在提交前书面说明。 |
| 2 | **所有可见按钮都有真实动作** | Web 与小程序每个按钮、链接、图标按钮都有可点击事件，调用真实 API 或进入真实页面；**禁止**「点击无反应」「仅 toast『成功』」「只改 localStorage」三类假按钮。 |
| 3 | **页面跳转与返回状态正确** | 列表 → 详情 → 返回保留滚动位置与筛选；新建/编辑/确认/退回/完成 全部走通；返回时已变更的字段回显，**不出现白屏、404、错误堆栈**。 |
| 4 | **后端接口与数据库落表正确** | API 字段、状态码、事务边界与 Service 一致；Alembic 迁移**新增**（不改写历史）；关联表外键、unique、显式 ID 均与基准一致；**前后端联通测试通过**。 |
| 5 | **权限/状态/版本/幂等校验正确** | Service 层是权限边界（不是前端按钮）；任务类操作校验 `task_version`；卡片/汇报/动作幂等（同一 request_id 不重复落库）；状态机不允许跨级变更。 |
| 6 | **手机端没有横向溢出** | 在 320px / 360px / 375px / 414px 宽度下，所有页面均无横向滚动条，文本不截断为乱码；小程序按 `rpx` 规范实现。 |
| 7 | **加载/空态/错误/无权限状态完整** | 每个列表页都有「加载中」「空数据」「请求失败」「无权限」四态；空态有引导文案；错误态可点击重试；无权限显式提示而**不是空白**。 |
| 8 | **自动化测试通过** | 后端 `pytest` 全绿、`ruff check` 0 报错、`pip check` 干净；前端 `npm run lint && npm run test -- --run && npm run build` 全绿；迁移合同 0 失败；PostgreSQL opt-in 通过（或显式说明未启用的原因）。 |
| 9 | **代码包结构能被微信开发者工具识别** | `wechat-miniprogram/` 与 `wechat-miniprogram-standalone/` 在最新版微信开发者工具中能正常打开预览；`app.json` 字段合法；所有 WXSS / WXS 通过 `node --check`；没有跨包引用残留。 |
| 10 | **没有提前混入下一功能** | 本次提交只涉及任务卡允许修改的范围；未声明的字段、表、按钮、路由、AI 接口都不允许出现；如确实需要扩展，必须先把任务标 `BLOCKED` 并说明。 |

### 2.1 本项目特殊口径（功能 12「绩效/优先级/负荷/冲突」已锁定）

下列参数是功能 12 的硬性上限，**任何调整必须重新发起需求评审**：

```text
绩效总分 = 类型 25% + 事业部 25% + 指标名称 25% + 定义/公式 20% + 交付物 5%
文本相似度：中文字符 2~4 gram TF-IDF + 余弦相似度 80% + 关键词覆盖率 20%
关联阈值：>=80 强相关；50~79.99 弱相关；<50 无明显相关
优先级：重要性 = 任务权重 45% + 正式绩效 35% + 汇报层级 20%
       紧急性 = 时间压力 60% + 逾期 25% + 突发 15%  → 默认阈值 70
负荷五维：剩余工时 40% + 权重 25% + 任务数 15% + 突发 10% + 受阻/逾期 10%
remaining_hours：按 Asia/Shanghai 工作日每日容量窗口计算，无节假日表时不得编造 09:00~18:00 班次
冲突检测：覆盖容量、截止集中、依赖、突发挤占；estimated_hours 不参与；消失的冲突转 resolved，不删历史
创建人选择「不关联绩效」必须真实清除后端正式确认关系，不能只是前端本地状态
任务级 / 节点级 / 工作台 优先级一律由后端预算并落表，客户端禁止复制公式
```

## 3. 提交验收前的「全量回归」义务（第 11 条）

单功能通过不等于可提交。每个功能验收前，**必须**把「功能 01 ~ 当前功能」全量串联回归：

| 回归检查项 | 必跑内容 |
|---|---|
| 页面跳转 | 入口页 → 中间页 → 详情页 → 返回，每条路径在 Web 与小程序两端都验 |
| 筛选参数 | 日期范围、状态、责任人、标签、看板视图筛选条件保留与回显 |
| 数据传递 | 列表 → 详情 → 编辑 → 保存 → 再打开，字段值不丢失不错位 |
| 状态变化 | 草稿/确认/退回/进行中/完成/验收各阶段操作与文案一致 |
| 返回恢复 | 后退栈、浏览器返回键、小程序左上角返回均恢复到进入前的列表/筛选 |
| 性能 | 列表 100 条以内首屏 <1.5s，无控制台错误与未处理 Promise rejection |
| 联调 | 后端 `pytest`、前端 `vitest`、Alembic 迁移、小程序 `node --check` 全绿 |

> **全量回归不通过，不得打包给用户体验；用户体验通过后，才允许进入下一功能开发。**

## 4. 提交形态与交付清单

每个功能提交时，仓库内必须新增或更新下列材料：

```text
1. FEATURE_<N>_ACCEPTANCE.md        # 单功能验收记录（参照 FEATURE_12）
2. 表迁移（新增的 alembic 修订号）                # 不允许改写历史
3. tests/ 下新增的单元 + 集成测试                    # 必须真实断言，不允许 skip 伪装
4. wechat-miniprogram-standalone/docs/<feature>/  # 单功能在小程序独立版的截图与验收
5. README / API 文档中暴露的字段、状态码、错误码
```

## 5. 严禁条款（违反任一即不算通过）

- ❌ 一次实现多个未验收功能，禁止「顺手做了下一项」
- ❌ 删除测试、降低断言、用 `skip` / `xfail` 伪装通过
- ❌ 把第二版 HTML 放进 `iframe` / `dangerouslySetInnerHTML` / 作为生产入口直接运行
- ❌ 把点击无反应、假成功提示、只改 localStorage 的按钮留在最终版本
- ❌ 在前端复制状态机、权限、优先级或负荷计算规则
- ❌ 重写已有 Alembic 历史迁移；所有结构变更必须新增迁移
- ❌ 在代码、测试输出或文档中写入真实密码、Token、Secret、API Key 或完整数据库连接串

## 6. 复审与升级路径

如果任一条件判定失败：

1. 在 `FEATURE_<N>_ACCEPTANCE.md` 末尾记录「失败原因 + 复现步骤 + 影响范围」。
2. 把任务卡状态置回 `IN_PROGRESS`，并在 `DEVELOPMENT_PLAN_V1.1.md` 第 N 任务的「验收证据」里追加。
3. 修复后从第 2 节「单功能硬性条件」开始全部重跑，**不允许只补一项**。
4. 修复涉及业务口径变化时，必须先回到第二版 PRD-V1.1 进行裁决，必要时升级到用户确认。

---

> **一句话总结**：每一个功能都按本 10 + 1 条标准完整交付；逐项验证通过、回归通过、打包给你体验；你点头之后再开发下一个。
